# XrayLarch Web V1 Design

**Date:** 2026-08-17
**Status:** Architecture approved; implementation pending

## Goal

Provide a browser-based, mouse-first XAS processing workbench powered by the
existing `xraylarch` library. A scientist can upload one spectrum, explicitly
map its data columns, inspect raw data, preview deterministic processing changes,
apply a recipe revision, and inspect the resulting normalized spectrum, χ(k), and
χ(R) plots without installing the desktop GUI.

## Product principles

1. Larch performs all numerical work. The browser only supplies validated inputs
   and renders server-produced data.
2. Preview is never an implicit mutation. Applied state remains visible while a
   draft is being edited or when a preview fails.
3. Every scientific value has a unit, and automatic choices are visible and
   overridable.
4. The web app is a real workbench: upload, inspect, adjust, compare within a
   recipe history, and download data are primary flows. Tours and chat are out of
   scope for V1.
5. Existing Larch scientific defaults and calculations are not changed by the web
   layer.

## Scope

### Included in V1

- A standalone FastAPI backend and Next.js App Router frontend in this repository.
- Upload of bounded text/CSV/XDI-style XAS files through an HTTP multipart endpoint.
- File inspection with safe filename display, point count, ordered numeric columns,
  candidate signal roles, units when available, and monotonicity warnings.
- Explicit selection of the energy column and μ/signal column. A clear heuristic
  may preselect values, but ambiguous mappings require confirmation.
- A single active spectrum per browser workspace, with raw input and applied recipe
  revisions retained for that workspace.
- Deterministic processing through Larch `pre_edge`, `autobk`, and `xftf`.
- Draft controls for E0, pre-edge/post-edge regions, normalization degree,
  `rbkg`, k-range, shared k-weight, stage-specific FFT taper/window settings,
  and output range.
- Linked raw/normalized μ(E), χ(k), and χ(R) Plotly views with derived values such
  as E0 and edge step.
- Preview, cancel, apply, and restore-as-new-revision behavior.
- Download of the active processed arrays and recipe as CSV/JSON.
- Focused backend tests, frontend unit tests, TypeScript checks, production build,
  and browser smoke tests at desktop and narrow widths.
- A manually activated, isolated Dr.XAS workstation deployment.

### Explicitly deferred

- XRF, XRD, map/image viewers, FEFF execution, multi-path fitting, and pre-edge
  peak fitting.
- Multi-file alignment, merge, batch processing, and comparison across independent
  source files.
- Chat or LLM orchestration.
- User accounts, public sharing, and internet-facing authentication.
- Automatic Git watcher, cron job, reverse proxy, firewall rule, database, or
  shared Dr.XAS data-store access.

V1 is a trusted-network, single-user workstation application. The deployment must
not be presented as suitable for public or multi-tenant data before authentication
and authorization exist.

## Architecture

```text
Browser
  │ same-origin Next routes
  ▼
Next.js frontend :3004
  │ server-side BACKEND_URL
  ▼
FastAPI backend :8006 (loopback only)
  │
  ├── xraylarch library: read → pre_edge → autobk → xftf
  └── /local/apps/xraylarch-web/data/<workspace-id>/
```

The frontend is a Next.js 14 App Router application using React, TypeScript,
Tailwind, and `react-plotly.js`. Its catch-all backend proxy keeps the browser
same-origin and prevents frontend code from needing CORS or direct knowledge of
the backend listener. The backend is Python/FastAPI with Uvicorn and installs the
repository's Larch package into a release-local virtual environment.

The backend is the authority for parsing, validation, processing, revision
identity, and stored workspace state. The frontend owns transient form state and
view selection but rehydrates from the backend after refresh.

## Workspace and revision state

Each workspace has an opaque ID generated by the backend. The browser stores only
that ID in local storage and sends it on subsequent requests. The backend stores
the uploaded source, normalized metadata, applied revisions, and derived arrays in
the workspace's private state directory. Workspace directories are mode `0700`;
the release directory never contains mutable user data.

The state model has two layers:

- **Applied state:** the current source mapping, processed arrays, recipe, and
  immutable revision ID.
- **Draft state:** an unapplied recipe, preview arrays/values, warnings, and the
  source revision used to produce that preview.

Applying a draft creates a new revision linked to its parent. Restoring an earlier
revision creates another revision; it never deletes later history. Apply requests
include the expected parent revision, and a stale parent returns HTTP 409 without
changing the active result.

The first implementation may serialize workspace state as validated JSON plus
NumPy-compatible array files; it must not use pickle or execute uploaded content.

## Scientific processing contract

The backend creates a fresh Larch `Group` for every preview or apply operation so
one request cannot mutate another request's arrays. It validates the selected
columns before processing:

- energy and signal arrays have equal non-zero length;
- values are finite after the parser's explicit handling of rejected rows;
- energy is strictly increasing, or the response is `blocked` with a repair action;
- the point count and serialized request remain within configured limits;
- all ranges are finite, ordered, and within a permitted relationship to the data;
- `kmax > kmin`, `rbkg > 0`, and integer weights/degrees are within bounded ranges.

The processing sequence is:

1. Construct the selected `energy` and `mu` arrays without changing the raw source.
2. Run `pre_edge` with the recipe's explicit overrides and preserve Larch's
   automatic values when a field is `null`.
3. Run `autobk` using the same E0/edge-step result and the recipe's `rbkg`, k
   bounds, shared k-weight, and optional Autobk taper/window overrides.
4. Run `xftf` on the resulting χ(k) using the recipe's Fourier taper/window
   settings and shared k-weight.
5. Serialize only finite, JSON-safe numeric arrays and derived scalar values.

The web defaults preserve the function-specific Larch behavior: shared k-weight 2
matches the established XAS processing pipeline, Autobk taper/window remain
automatic unless explicitly overridden, and Fourier taper/window default to the
Larch XAS transform defaults (`dk=1.0`, `window="kaiser"`). The UI labels the
shared k-weight and any unified display choice as product-level controls. The
backend records the exact effective values returned by Larch, including automatic
E0, edge step, and stage-specific settings. No web-only duplicate of the XAS
algorithm is permitted.

## HTTP API

All application routes are under `/api`. Error bodies use one shape:

```json
{
  "error": {
    "code": "invalid_mapping",
    "message": "Choose one energy column and one signal column.",
    "fields": {"energy_column": "required"},
    "recovery": "Select the columns in the import panel and retry."
  }
}
```

The initial API surface is:

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/health` | Backend health and version metadata; no workspace access |
| POST | `/api/workspaces` | Create an empty workspace |
| POST | `/api/workspaces/{id}/uploads/inspect` | Parse an upload and return column/quality inspection |
| POST | `/api/workspaces/{id}/mapping` | Confirm energy/signal mapping and create source revision |
| GET | `/api/workspaces/{id}` | Rehydrate workspace, current applied result, and history |
| POST | `/api/workspaces/{id}/preview` | Validate draft recipe and return temporary curves/values |
| POST | `/api/workspaces/{id}/apply` | Apply a draft against an expected parent revision |
| POST | `/api/workspaces/{id}/restore` | Create a new applied revision from a prior revision |
| GET | `/api/workspaces/{id}/revisions/{revision}/data.csv` | Download arrays for one revision |
| GET | `/api/workspaces/{id}/revisions/{revision}/recipe.json` | Download effective recipe and provenance |

The Next frontend proxy exposes the same paths under `/api/backend/*` and does not
forward arbitrary browser-controlled upstream URLs.

## UI design

The main page has four persistent regions:

1. **Spectrum tray:** filename, source status, active revision, point count, and
   import warnings.
2. **Plot canvas:** tabs or linked cards for raw μ(E), normalized μ(E), χ(k), and
   χ(R). Plotly JSON from the backend is rendered directly; the frontend never
   reconstructs scientific arrays from display labels.
3. **Processing inspector:** Import and Normalize/EXAFS sections with Recommended
   controls first and Advanced controls expandable. Stage-specific Autobk and
   Fourier taper/window overrides remain in Advanced. Every field shows units and
   a short explanation.
4. **Recipe history:** applied revisions with parameter diffs, effective values,
   restore action, and download actions.

The visible state vocabulary is `Ready`, `Review`, `Blocked`, or `Not current`.
Draft changes show `Preview available` only after a successful server response.
The Apply button names the active source and parent revision. Failed previews keep
the last applied plots visible and mark only the affected controls.

The UI must work at 1440×900 and 1280×720 without page-level horizontal scrolling,
and at a narrow viewport with stacked inspector and plot regions. Animations honor
`prefers-reduced-motion`. Long filenames are safely truncated visually but remain
available through an accessible title/tooltip.

## Failure and privacy behavior

- Upload parsing rejects executable/non-text content and reports the failed file by
  sanitized display name only.
- Ambiguous columns produce a selectable warning, not a guessed applied result.
- Invalid energy order blocks processing and preserves the source upload.
- Preview exceptions are sanitized into stable error codes; raw tracebacks stay in
  server logs and never reach the browser.
- A stale Apply returns 409 and leaves the existing applied result unchanged.
- Workspace files are private to the service account and stored outside releases.
- The app does not read Dr.XAS authentication, provider secrets, databases, or
  shared file stores.
- V1 has no multi-user authorization; deployment documentation must state the
  trusted-network boundary and the future authentication requirement.

## Testing and acceptance

### Backend

- parser/inspection tests for numeric columns, headers, malformed rows, filename
  sanitization, and monotonicity;
- recipe validation tests for bounds, units, automatic values, and error shape;
- processing regression tests using a checked-in small XAS fixture, including raw
  array immutability and finite output arrays;
- revision tests for preview non-mutation, apply, restore-as-new, and stale-parent
  conflict;
- API tests for workspace isolation, download content, and sanitized failures;
- no network calls and no shared database dependency.

### Frontend

- reducer/state tests for applied versus draft state, preview cancellation, stale
  response rejection, and rehydration;
- component tests for column mapping, warning/blocked states, control units,
  history restore, and plot selection;
- TypeScript check, Vitest suite, and production Next build;
- Playwright smoke test: create workspace → upload fixture → map columns → preview
  → apply → restore → download, using `domcontentloaded` plus explicit readiness
  checks rather than `networkidle`.

Acceptance requires the complete flow to work without chat or desktop Larch, all
scientific processing to run through Larch, and the last applied result to remain
visible after a deliberately invalid preview.

## Dr.XAS deployment contract

The deployment is manual and isolated under the generic Dr.XAS web-app playbook:

```text
slug: xraylarch-web
frontend_listen: 0.0.0.0:3004
frontend_health: 127.0.0.1:3004
backend_listen: 127.0.0.1:8006
external_url: http://drxas.xray.aps.anl.gov:3004
release_root: /local/apps/xraylarch-web/releases
current_symlink: /local/apps/xraylarch-web/current
state_root: /local/apps/xraylarch-web/data
screens: xraylarch-web-frontend, xraylarch-web-backend
health: /, /health, /api/backend/health
```

The deployer must build an immutable release, use a release-local Python
environment, run `pip check`, install/build the frontend with the host's Node 20
environment, start only the two namespaced screens, and update `current` only after
all health checks pass. It must never use the existing Dr.XAS ports/services,
watchers, cron, firewall, reverse proxy, shared database, or shared data root.

Deployment success requires the intended Git revision, current symlink, saved
successful revision, listener ownership, named screens, frontend HTTP 200,
backend health JSON, same-origin proxy health, and existing Dr.XAS service health
to agree. A failed activation retains the previous release and does not advance
success state.

## Non-goals and future extensions

The following are deliberately separate design cycles: authentication and sharing;
multi-spectrum trays with calibration/alignment/merge; batch recipes; XANES/pre-edge
peak tools; EXAFS fitting/FEFF; XRF/XRD applications; and chat orchestration. Their
interfaces must not be smuggled into V1 through generic “advanced” controls.
